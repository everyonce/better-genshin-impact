# Keeping Open P2P loaded between photo requests

The earlier two-batch [street patrol](BetterGI-Patrol-Learning-2026-10-29.md) measured 24.84 seconds between its last and next input dispatch. The second CUDA model load accounted for 18.47 seconds. This experiment serves distinct photo requests from one bounded resident lease on SIREN's existing minimized RDP desktop.

## Qualification

Before launch, freeze the request names, target stations, IDs and circuit counts. Keep the surveyed route, walking-goal embedding, Open P2P weights and qualified generation-four landmark recognizer fixed. The changing user objective is which verified photos to collect. Each request must produce its own original images and native-source evidence. The final station frame and acknowledged release of request one belong to that request. Request two must use fresh source frames, and its controller actions must join their own receipts.

A successful handoff uses one GPU load and one controller lease. The independent audit must pass both photo objectives and measure less than one second from the last applied dispatch of request one to the first applied dispatch of request two. Keep the existing 150 ms source-to-dispatch limit, zero-loss recording check, 78 °C cutoff, authenticated root and child binding and operator stop. In a separate stop drill the operator stop must address the active resident after a confirmed input from request two, release input, and produce evidence of an incomplete second objective.

The timing measures software input dispatch. The camera, game and display introduce additional latency. Keep the full request and stop evidence under `artifacts/live/2026-10-29-warm` on SIREN.

## First live handoff

The first request visited the west lamp for a photo and completed two circuits. The second collected new photos at the stairs and junction over the next two circuits. All 16 legs and three original photos verified. Each request accounted for 259 applied actions. Open P2P loaded once, and the GPU reached 62 °C.

The last old-request dispatch and first new-request dispatch were **548.47 ms apart**. Independent reconstruction from Windows performance-counter time and the original WGC capture timestamps gave the same interval. The final verified source frame lay 351.25 ms after the old dispatch and 197.22 ms before the new one. The two ordinary stair returns in the same recording took 595.78 and 699.77 ms between dispatches. The maximum image-to-dispatch ages in the two requests were 143.40 and 139.17 ms.

The original supervisor refused the final audit because its held-key reader expected a string. The native terminal evidence contained an empty array, complete input telemetry and a successful release call. The corrected verifier requires those exact observations and independently passed the original sealed recording. Both the initial refusal and corrected audit are retained in `full/warm-20261029T154845Z-eb5f28cbd5bf`.

## Sustained run

Two distinct requests each ran twelve circuits. The first collected the junction and stair front. The second collected the west lamp and a fresh image at the stairs. In **368.89 seconds** the resident completed 96 verified legs, recorded 7,964 original frames and applied 3,160 actions on one GPU model load and one controller lease. The model load took 18.31 seconds before gameplay. Median policy evaluation was 30.83 ms. Capture to first software dispatch was 82.28 ms at the median and 144.94 ms at the maximum. The GPU peaked at 64 °C.

The handoff after leg 48 took **598.80 ms**. The other 22 stair returns followed by a new dispatch had a median interval of 605.90 ms and a range of 597.81 to 708.95 ms on the same lease. Both requests supplied all their requested photos. The landmark observer correctly named 92 of 97 unique station views. The independent video replay reproduced all 97 class predictions. The evidence is under `sustained/warm-20261029T155122Z-3a81fdc8d26f`.

Consecutive dispatches within requests were 99.90 ms apart at the median. The longest interval anywhere in the sustained run was 807.17 ms, including station releases. Native receipt time and independently anchored WGC time agreed on the request-switch interval.

## Operator stop

In a separate two-request test, the west-lamp objective completed one circuit. The second objective began on a fresh frame and applied 18 actions before the addressed stop. The supervisor created the external STOP marker after observing an applied-input receipt from that request, then published the stop to the exact active resident. Native Windows performance-counter measurements bracketed the atomic write.

The bridge returned its final software release **36.02 to 37.43 ms after the addressed write**. Its final ledger reported an empty held-key array, no active action and a successful return of the release call. This interval begins at control-file publication. An operator who creates a STOP file separately must also allow for the supervisor to observe it. The audit marked the stop verified and the interrupted request incomplete. Evidence is under `stop/warm-20261029T160332Z-17ff39777f3a`. Final discovery found the original minimized host and the original game-ready RDP child, with no active stream or task.
