# Prepared request recovery (inactive candidate)

This extension targets pauses caused by a relay losing its reply after the CLI has already submitted a command. It records the exact inner command before submission. A later, read-only reconciliation may settle a positively proven completed command without issuing a second command. It does not shorten combat, dialogue, travel, observation freshness, or quiescence requirements.

No production adapter, automatic retry loop, native collector, process/pipe reader, or activation is included. The current live controller remains the sole input owner. Unit results establish the protocol behavior with synthetic evidence; they do not establish shorter live pauses or physical input delivery.

- The canonical CLI preimage is SHA256 `3020158ceaa7610bf081a1c5ccda86b3159719a7cf4ffe069498347c351fca4a`. `canonical-cli-prepared.patch` also preserves the existing local one-second, same-byte Windows replacement retry and r2/r3 receipt-path grammar. These are explicit source composition changes; this patch is not a whole-file production adoption instruction.
- Both applications produce the same CLI postimage. The manifest contains its hash and all dependency hashes. Receipt maintenance remains before UUID creation; the existing canonical archive helper is unchanged.

## Required owner integration

1. Supply `owner_probe()` returning a verified `OwnerContext(session, process_id, windows_session_id, owner_lifetime_binding)`. The binding must come from authenticated current native status and a source-verified service-lifetime nonce contract. Use the same canonical field order, serializer, encoding and normalized application path on every read. A copied heartbeat, PID alone, cached status or hardcoded fingerprint is insufficient. The owner supplied fingerprint v1 as ordered fields version, processId, windowsSessionId, scriptSession, appDirectory, instanceType, instanceNonce, serialized with PowerShell ConvertTo-Json -Compress and hashed as UTF-8 SHA256. appDirectory is the Windows full path with trailing backslashes removed and invariant lowercase. The actual key is appDirectory. This opaque protocol does not implement a second serializer; exact cross-language canonicalization and the authenticated provider remain owner qualification work.
2. Construct `PreparedRelayJournal` with an existing dedicated journal directory, the allowed quest-step set and the legacy response directory. Every relay instance must use the same persistent OS lock. `dispatch(outer, owner, prepare)` must call the guarded CLI as `main(before_request_write=prepare)` while that lock is held. Keep the current line-loop/close handling and one-request-in-flight rule. The portable extension admits only `observe` and approved `questStep` envelopes.
3. The callback persists a global active marker, outer intent, inner UUID claim and exact UTF-8 request bytes/hash. It checks owner identity and the CLI's original guarded heartbeat, reads the mapping back, then returns an acknowledgment. The copied CLI checks the acknowledgment and, immediately before every actual `os.replace` attempt, rereads `require_live_controller` with the same original session/frame and passes that fresh heartbeat to `revalidate(current_heartbeat)`. The closure validates both original and current heartbeat freshness and calls `owner_probe(current_admission=<fresh heartbeat>)`. In this mode the trusted owner adapter must freshly authenticate native status, compare PID/WTS/remoteDesktop/scriptSession/frame/idle state/active-request and service ownership to that expected admission, and return the opaque OwnerContext only after those checks. Identity-only reads elsewhere use `owner_probe()` without that keyword; they must not require the old action frame during recovery. The adapter must not ignore current_admission. This keyword is a v2 process-local callback contract; persisted prepared-v1 record semantics are unchanged. UUID, original creation time and bytes are never renewed. A changed owner, expired original heartbeat, corrupt record or disk failure prevents further submission.
4. All consumers must call `validate_prepared_result` against the exact outer request and expected owner. An ID-only legacy response, unknown outcome or unbound envelope is insufficient. Cached and recovered results are historical outcomes; they do not grant a new action lease.
5. Only the owner may implement and invoke the read-only `collect_proof(prepared)` adapter. It has no CLI/submission path. For a matching unknown active intent, `reconcile` accepts two stable positive completion samples, persists a separate recovery record and retires the active marker only after that bound settlement is durable. The original unknown response is preserved.

## Recovery evidence contract

Each trusted collector sample contains `ownerBefore`, `ownerAfter`, wall-clock `readAtMs`, monotonic `monotonicMs`, and the raw JSON strings `requestUtf8`, `receiptUtf8`, `observationUtf8`, `latestObservationUtf8`, `heartbeatUtf8`. Two samples must span the existing 400 ms stable-quiescence interval, no more than five seconds, with unchanged request, terminal receipt, immutable observation and latest-observation bytes. Owner checks bracket both samples and the journal validates the owner again after collection.

The current request must exactly equal the durably prepared bytes. The receipt must positively identify the same completed inner UUID, session and mission. Its immutable observation must be retained, have the same terminal frame, a frame strictly after the request's expected frame, and valid original chronology. Latest observation and fresh heartbeat must agree on the same session/frame, actual PID and Windows session, idle state and no active request. Stale, future, foreign, malformed, missing, changing or unquiescent evidence keeps the entire journal held.

The existing producer receipt supplies ID/session/mission/status/frame/time but does not echo an accepted-request digest or owner fingerprint. Its terminal receipt is written before the final input-release/idle sequence. Immutable observation JSON may be deferred or later pruned. Therefore a completed receipt alone is insufficient. Missing evidence never proves non-submission, and an old/pre-request frame, failed/stopped/rejected receipt, changed lifetime or missing immutable artifact cannot be automatically recovered by this version. The owner must review these source guarantees against the loaded implementation before admission.

Native accepted-request binding and a durable terminal-plus-quiescence fence would strengthen this contract; neither is claimed or implemented here. Current recovery remains a conditional inference from the exact prepared request, retained positive producer evidence, unchanged verified owner and stable idle samples. No action is replayed to repair missing proof.

## Validation and retention

Run `python -B -m unittest -v test_relay_prepared test_relay_reliability` beside the copied CLI and modules. The packet records 41 prepared/recovery/actual-CLI cases plus 25 canonical relay cases (66 distinct tests). The validation manifest records measured run results for this v3 source, separately from the frozen v1 runs; repeated compatibility runs are not distinct additional tests.

Tests use synthetic owners/files, mocked native gates, an actual cross-process journal lock and an actual child process exiting after one synthetic effect. They cover crash boundaries, global holds, durable inner UUID claims, malformed acknowledgments, archive deferral before UUID creation, wrong owner/bytes/frame/step, changed evidence, same-byte Windows retries, owner loss during retry, busy or advanced current admission, native ownership rejection, expired original heartbeat despite a fresh replacement heartbeat, and historical recovery without timestamp renewal. Reparse cases are deterministic metadata simulations and do not claim an elevated Windows symlink test.

The journal does not delete evidence or automatically clear uncertain work. Retention/compaction must be separately coordinated around settled records; active intents, claims, mappings and recovery evidence remain protected. Packaging cleanup removes only verified generated duplicate/scratch copies. Frozen source, tests, review evidence and rollback preimages are retained.

V3 retains the v2 callback contract and closes two independent-review findings. A retry checks its original monotonic deadline after fresh revalidation, before another actual replacement; the first-attempt behavior is unchanged. The original Windows sharing error is preserved, and request/heartbeat/UUID timestamps are not renewed. Test fixtures resolve the physical temporary directory and controlled child processes explicitly add only their trusted source directory under inherited safe-path settings. Runtime path validation is unchanged.
